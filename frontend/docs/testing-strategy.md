# 프론트엔드 테스트 전략

코드 변경 뒤 기존 사용자 흐름이 유지되는지 병합 전에 빠르게 확인하는 기준입니다. 구현 세부 사항보다 사용자가 관찰하는 동작과 프론트엔드가 지켜야 할 API 계약을 검증합니다.

## 1. 목표

- 로그인, 매물, 체크리스트, 지도처럼 실패 영향이 큰 흐름을 자동으로 검증합니다.
- 순수 로직은 작고 빠른 단위 테스트로 원인을 좁힙니다.
- 화면 리팩터링은 내부 컴포넌트 구조가 아니라 접근 가능한 역할과 사용자 동작을 기준으로 보호합니다.
- 실제 브라우저·WebView에서만 발견되는 문제는 별도의 수동 점검 범위로 명시합니다.

## 2. 테스트 계층

| 계층      | 대상                                                        | 도구와 위치                                                     | 작성 기준                                        |
| --------- | ----------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------ |
| 단위      | 포맷팅, 폼 검증, 인증 저장소, 지도 계산 등 순수 로직        | Vitest, `*.test.ts`                                             | 입력과 출력만으로 검증할 수 있을 때              |
| 컴포넌트  | 공통 UI, 포커스 이동, 다이얼로그, 이미지 로딩               | React Testing Library, `test/**/ui/**/*.test.tsx`               | 독립된 상호작용이나 접근성 계약이 있을 때        |
| 화면 통합 | 라우팅, React Query, API 성공·실패·재시도, 주요 사용자 흐름 | React Testing Library + MSW, `test/app/router/*Routes.test.tsx` | 여러 컴포넌트와 서버 상태가 함께 동작할 때       |
| 계약      | API 파서와 MSW fixture가 실제 응답 형식을 넘지 않는지 확인  | Vitest, `test/features/**/api`, `test/app/mocks`                | API 응답 필드나 DTO가 바뀔 때                    |
| E2E·시각  | 실제 브라우저, 지도 SDK, WebView, 반응형 레이아웃           | 현재 수동 점검                                                  | 브라우저 엔진·외부 SDK·레이아웃 확인이 필요할 때 |

컴포넌트 내부 함수나 CSS 클래스 이름은 직접 테스트하지 않습니다. 사용자가 접근하는 버튼, 링크, 입력 필드, 메시지와 이동 결과를 검증합니다.

## 3. 주요 기능 보호 범위

| 기능                     | 자동화 테스트                                                 | 핵심 검증 내용                                   |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------ |
| 인증과 보호 라우트       | `AppRoutes.test.tsx`, `authStore.test.ts`                     | 로그인, 만료, 401, 로그아웃, 잘못된 경로         |
| 매물 CRUD·메모·사진·비교 | `PropertyRoutes.test.tsx`                                     | 등록·수정·삭제, 빠른 메모, 사진 관리, PDF 비교   |
| 체크리스트               | `ChecklistRoutes.test.tsx`                                    | 생성·수정·적용, 상태와 메모 저장, 실패 복구      |
| 지도와 위치              | `MapRoutes.test.tsx`, `MapCanvas.test.tsx`, `mapApi.test.ts`  | 주소 검색, 위치 선택, 핀·주변 시설, SDK 오류     |
| API 계약                 | `apis/*.test.ts`, `contractShape.test.ts`, `handlers.test.ts` | 응답 파싱, 오류 코드, 목과 실제 계약의 필드 일치 |
| 분석·네이티브 분기       | `PostHogTracker.test.tsx`, `nativeApp.test.ts`                | 페이지 이벤트, 사용자 식별, WebView 분기         |

## 4. 변경 유형별 기준

- 순수 함수 추가·수정: 정상값, 경계값, 잘못된 값의 단위 테스트를 작성합니다.
- API 변경: 파서 테스트와 `contractShape.test.ts`를 먼저 수정하고 화면 통합 테스트를 갱신합니다.
- 화면 기능 추가: 성공 흐름뿐 아니라 로딩, 빈 결과, 실패, 재시도 중 필요한 상태를 테스트합니다.
- 리팩터링: 기존 화면 통합 테스트가 그대로 통과해야 합니다. 새 책임이 독립적인 사용자 상호작용을 가지면 해당 테스트를 추가합니다.
- CSS 변경: DOM 구조나 클래스 스냅샷 대신 접근 가능한 이름과 상호작용을 자동 검증하고, 모바일 폭은 실제 렌더링으로 확인합니다.

## 5. CI와 완료 조건

PR과 `develop`·`main` 반영 시 GitHub Actions가 다음 순서로 실행합니다.

```bash
npm run lint
npm run format:check
npm test
npm run build
```

작업 완료 조건은 다음과 같습니다.

1. 변경 위험에 맞는 자동화 테스트가 추가되거나 기존 테스트로 보호되는 이유가 설명되어 있습니다.
2. 린트, 포맷, 전체 테스트, 타입 검사를 포함한 운영 빌드가 통과합니다.
3. 지도·파일 다운로드·WebView처럼 jsdom이 재현하지 못하는 변경은 실제 브라우저 또는 기기에서 확인합니다.

## 6. E2E 도입 기준

현재 주요 도메인 흐름은 React Testing Library와 MSW 통합 테스트로 빠르게 검증합니다. 다음 문제가 반복되면 Playwright 같은 실제 브라우저 E2E를 추가합니다.

- Webpack 산출물에서는 발생하지만 jsdom에서는 재현되지 않는 회귀
- 로그인부터 매물 등록까지 전체 흐름의 배포 후 장애
- 지도 SDK, 파일 다운로드, 브라우저 권한처럼 실제 브라우저가 필요한 기능의 반복 장애

처음 도입할 E2E는 로그인 → 첫 매물 등록 → 상세 확인 한 경로로 제한하고, 안정화한 뒤 체크리스트와 지도로 확장합니다.
