# 랜딩·월세·목적지 서칭 측정 기준

## 목적과 적용 순서

월세 조회는 관심 지역의 실제 거래 목록 확인까지, 목적지 서칭은 조건에 맞는 동네를 고르고 대중교통 경로 확인까지 측정한다. 클릭 의도와 실제 결과 표시를 구분한다.

분석 브랜치 `feat/343-exploration-analytics`는 최신 `origin/develop`의 랜딩·공개 탐색 병합(#371, `0b5c3be4`) 위로 재배치했다. 공개 경로, 로그인 후 방 기록 연결, 검색 복원, 동적 `mapPath`를 유지하면서 로그 호출을 합쳤다. 백엔드와 로그인 정책은 변경하지 않는다.

로컬 미완성 작업에서 수집 보강과 API 오류 경계만 이식했다. 원래 작업 폴더의 변경은 그대로 두고, 이미 develop에 반영된 수집 구조 분리(#344)와 청크 P2 분류는 중복 적용하지 않는다.

- `useNeighborhoodPreview`: 검색 실행·재시도·동네 선택·정류장 변경을 수집한다. 검색 응답은 시도당 한 번만 기록한다.
- 월세·경로 상세 페이지: 실제 정보 표시와 실패를 구분하고 기존 공개 라우팅을 유지한다.
- `UsageGuidePage`: `useUsageGuideViewTracking`으로 방문 이벤트 중복을 막는다.
- `UsageDemo`: 직접 누른 탐색 모드 버튼만 수집한다. 스크롤로 재생되는 시연을 실제 기능 사용으로 기록하지 않는다.
- 랜딩을 없애면서 `landing_page_viewed`, `service_introduction_viewed`, `landing_cta_clicked`, `landing_demo_interacted`는 더 이상 보내지 않는다. 이전 기간 데이터를 볼 때만 쓴다.

선행 랜딩 변경이 병합되어 별도 적용 패치는 제거하고 실제 코드에 반영했다. 제거한 준비 패치는 Git 이력에서 복구할 수 있다.

## 공통 집계 기준

기본은 최근 14일, `environment=production`, 내부·테스트 코호트 `520731` 제외다. 익명 사용자와 로그인 사용자를 포함한다. 광고 여부는 제한하지 않는다. 로그인 식별 병합은 기존 SDK 구현을 이용한다.

고유 사용자 수는 선택 기간 전체에서 중복 제거한다. 일별 DAU를 더하거나 사용자 수와 세션 수를 나누지 않는다. 동일 사용자가 웹과 앱 모두 사용하면 플랫폼별 수치를 단순 합산하지 않는다. 개발 검증은 대시보드 환경 필터를 development로 바꾸며 mock 응답을 확인하려면 해당 시리즈의 `mock_data=false` 필터도 해제해야 한다.

통근 검색에는 `max_minutes`, `max_transfers`를, 월세 검색에는 `max_rent_manwon`을 수집한다. 주소·목적지 이름·좌표·검색어·정류장 ID·거래 금액 원문을 새 로그에 보내지 않는다. 상세 중복 방지에 사용한 지역/정류장 키는 로컬 비교용이며 전송하지 않는다.

검색 요청은 재시도마다 별도 ID를 만들고 결과는 시도당 한 번만 기록한다. 취소·자동 refetch·StrictMode로 결과 건수를 늘리지 않는다. 검색 복원으로 목록을 다시 연 것은 상세 확인으로 기록할 수 있지만 새 검색으로 꾸미지 않는다. 공개 탐색의 기존 `exploration_completed`는 지도 검색 결과 표시이며 월세·통근 서비스 사용 완료가 아니다.

## 대시보드 지표

[랜딩·월세·통근 탐색 대시보드](https://us.posthog.com/project/579863/dashboard/2210224)에 14개 지표와 배포 대기 안내를 저장했다. [원격 카드 ID와 정의 기록](exploration-analytics-dashboard.json)은 배포 설정이 아니라 측정 계약 기록이다.

| 지표                          | 분자                              | 분모·단위                  |
| ----------------------------- | --------------------------------- | -------------------------- |
| 전체 방문자                   | `$pageview` 사용자                | 기간 고유 사용자           |
| 월세 정보 확인율              | 거래가 있는 월세 목록 확인 사용자 | 월세 모드 지도 방문 사용자 |
| 전체 방문자 중 월세 확인 비율 | 거래가 있는 월세 목록 확인 사용자 | 전체 방문 사용자           |
| 목적지 서칭 완료율            | 경로를 실제 확인한 사용자         | 통근 모드 지도 방문 사용자 |
| 출발 정류장 변경률            | 다른 정류장을 직접 선택한 사용자  | 경로를 확인한 사용자       |
| 결과 없음 비율                | 통근 검색의 빈 결과 건수          | 결과 표시+검색 실패 건수   |
| 검색 조건 분포                | 검색 실행 건수                    | 통근 시간·환승 횟수별 건수 |
| 랜딩 클릭률                   | 랜딩에서 시작 버튼을 누른 사용자  | 랜딩 방문 사용자           |

기간 사용자 비율과 순차 퍼널은 다르다. 두 기능의 퍼널은 **지도 진입 → 검색 실행 → 동네 선택 → 정보 표시**이며 고유 사용자·ordered·1시간 전환 창으로 구성했다. 같은 검색 시도만 연결하는 엄격한 퍼널은 아니며 사용자가 한 시간 안에 재검색한 경우 다른 시도의 단계가 이어질 수 있다.

월세는 `has_transactions=true`만 완료로 계산하고 빈 목록은 별도 카드로 본다. 통근 경로를 동네 선택 직후 미리 불러오는 것은 완료가 아니다. 화면 진입이나 API 실패만으로 `commute_route_viewed`를 보내지 않는다. 정류장 기본 자동 선택·같은 정류장 재클릭도 변경으로 세지 않는다.

결과 없음 비율은 응답이 끝난 시도 기준이다. 진행 중·취소된 시도를 실패나 빈 결과로 취급하지 않는다. 통근 검색 조건 분포는 사용자 비율이 아니라 검색 건수이므로 반복 사용자 영향이 있다. 기능별 사용자와 여러 스토어 이동 사용자도 서로 겹칠 수 있다.

랜딩 클릭률은 신규 `page_kind=landing`을 분자에 적용한다. 과거 CTA에는 이 속성이 없으므로 새 로그 배포 전후 기간을 섞지 않는다. 스토어 클릭을 설치·앱 진입 성공으로 해석하지 않는다.

## 검증과 배포 후 확인

2026-10-14에 신규 계약용 14개 원격 쿼리를 재계산했고 실행 오류는 없었다. 신규 이벤트는 당시 수집 목록에 없었다. 따라서 신규 카드의 0%·빈 차트는 미수집 상태이며 성과 판정이 아니다. 지표 목표 수치는 팀에서 기준선과 실사용 피드백을 확보한 뒤 정한다.

자동 검사에는 검색 성공·빈 결과·실패·재시도·취소, StrictMode 중복, 캐시 재렌더, 실제 월세 목록 표시, 경로 프리패치와 표시 구분, 정류장 변경을 포함한다. 코드 검사 통과와 PostHog 실제 수신 확인은 별개다.

최신 develop에 통합한 코드로 린트·포맷·타입·전체 테스트·운영 빌드를 다시 검사한다. 구체적인 실행 결과는 아래 통합 검증 기록에 남긴다.

## 수집 보강과 오류 경계

### 웹·앱 구분

자취선배가 주입한 `window.__JACHWI_NATIVE_APP__.platform` 또는 전용 `JachwiSunbae/<version> ios|android` UA만 앱으로 판단한다. 일반 Android `wv`나 iOS의 Safari 문자열 부재만으로 앱으로 집계하지 않는다. 인스타 인앱 브라우저는 웹이다.

`jachwi-native-ready` 이벤트에서 등록 속성을 갱신하고, 자동 수집·예외 이벤트도 전송 시점에 기기 정보를 읽는다. `native_app_version`은 전용 UA의 앱 버전이며 브리지 프로토콜 버전과 다르다. 앱 표시가 전혀 없는 과거 이벤트는 이 코드로 소급 복원되지 않는다.

### 익명 테스트 트래픽

테스트 기기에서 `?analytics_test=1` 링크를 한 번 열면 같은 저장소의 다음 방문도 `traffic_type=test`로 수집한다. `?analytics_test=0`으로 해제한다. 개발 환경은 `development`, 그 외는 `external`이다. 저장소가 차단되면 현재 URL의 표시만 사용할 수 있으며 다른 기기·WebView 저장소로 전달되지 않는다.

이 표시는 권한·회원 여부와 무관한 이벤트 속성이다. 기존 내부 사용자 코호트에 자동으로 가입시키지 않으며 과거 테스트 이벤트도 자동 분류하지 않는다. 2026-10-15에 대시보드의 기존 운영 환경·코호트 제외를 유지하고 `coalesce(properties.traffic_type, 'external') NOT IN ('test', 'development')` 필터를 추가했다. 속성 없는 과거 이벤트를 유지하되 과거 테스트 트래픽이었다고 소급 확정하지 않는다. 14개 카드의 재계산이 오류 없이 실행됨을 확인했다.

### 행동 당시 로그인 상태

`auth_status=anonymous/authenticated`는 이벤트 속성이다. 로컬 인증 저장소에 세션이 없는지 기준으로 판정하며, 현재 회원 API 조회·SDK identify 완료 여부와 별개다. 서버의 권한 검증을 대체하지 않는다.

React 재렌더를 기다리지 않고 이벤트 호출 시 인증 저장소를 읽는다. 따라서 `setAuthentication` 직후의 `login_succeeded`도 authenticated로 기록한다. SDK 로딩 대기 큐에 들어간 수동 이벤트·스토어 클릭·예외는 호출 당시 값을 보존한다. 테스트 트래픽 표시도 호출 당시 값을 보존하여 전송 대기 중 표시를 해제해도 기존 테스트 이벤트가 외부 유저로 바뀌지 않는다. 자동 이벤트는 before_send에서 상태를 읽으며 이미 저장된 수동 이벤트의 상태를 현재 상태로 덮어쓰지 않는다.

익명 첫 방문은 SDK가 관리하는 ID를 유지하고 회원 조회 성공 시 기존 `member-{memberId}`로 identify한다. 로그아웃은 기존 reset 정책을 유지한다. 별도 사용자 ID나 fingerprint를 만들지 않는다. 웹·앱의 비로그인 ID가 같은 사람인지 추정해서 합치지 않는다.

지표는 전체 사용자(익명 포함)를 기본 분모로 두고 이벤트의 auth_status로 로그인 여부를 나눈다. 기간 중 같은 사용자가 로그인 전후 모두 행동하면 두 세그먼트에 포함될 수 있으므로 사용자 수를 단순 합산하지 않는다. 과거 auth_status가 없는 이벤트는 '미확인'으로 분리하며 현재 회원 프로필로 소급 채우지 않는다. 기존 대시보드의 분모를 로그인 사용자로 제한하지 않았다. 이 속성은 코드 배포 후부터 수집된다.

### API 오류

JSON·Blob API의 실패를 공통 경계에서 요청당 한 번 수집한다. 5xx는 P1, 정상 오류 계약의 4xx는 P2, 성공/오류 응답의 JSON·envelope·데이터 파서·Blob 계약 위반은 P1이다. 정상 취소와 종료된 인증은 제외한다. 응답 본문을 읽던 중 취소도 동일하게 제외한다.

쿼리·해시·숫자 ID·요청 본문·서버 메시지·원문 파서 예외는 새 API 오류 로그에 넣지 않는다. 기존 렌더링 오류 P0와 청크 오류 P2는 유지한다. 상세 기준과 Discord 알림 한계는 [에러 트래킹](error-tracking.md)을 따른다.

PR 브랜치는 푸시했으며 병합·배포는 별도 요청 전까지 진행하지 않는다.
