# 에러 트래킹 등급

PostHog 예외 이벤트의 `severity`는 대응 우선순위다. HTTP 성공 여부만으로 제품 동작의 성공을 판단하지 않는다.

| 등급 | 종류                 | 수집 기준                                                                                             |
| ---- | -------------------- | ----------------------------------------------------------------------------------------------------- |
| P0   | `uncaught`, `render` | 미처리 예외와 화면 렌더링 실패                                                                        |
| P1   | `api_server`         | HTTP 5xx                                                                                              |
| P1   | `api_contract`       | JSON 파싱 실패, 공통 envelope 누락, 데이터 파서 실패, 빈 응답·204 처리 실패, 잘못된 Blob Content-Type |
| P2   | `api_client`         | 정상 오류 envelope로 반환된 HTTP 4xx. 인증 만료·권한·입력 오류·리소스 없음·충돌·요청 제한도 기록한다  |
| P2   | `network`            | fetch 네트워크 실패                                                                                   |
| P2   | `chunk_load`         | JS·CSS 청크 로딩 실패                                                                                 |

4xx라도 응답 계약이 잘못되면 `api_contract=P1`이다. 사용자의 요청 취소(`AbortError`), 로그인하지 않은 상태에서 요청 중단, 로그아웃 후 늦게 도착한 응답은 정상적인 중단이므로 수집하지 않는다.

JSON 요청과 Blob 요청 모두 공통 API 경계에서 실패당 한 번 수집한다. 동일 요청을 다시 시도해서 실패한 경우에는 새 발생으로 수집한다. Query 재시도까지 포함하므로 수집 횟수는 오류를 겪은 사용자 수와 다를 수 있다.

## 기록하는 정보

- `source=api_request`, `error_category`, `severity`
- `request_method`, `request_path`: 쿼리·해시를 제거하고 숫자 ID를 `:id`로 치환한다.
- `response_status`: 응답이 있는 경우
- `error_code`: 영문 대문자·숫자·밑줄 형태의 서버 오류 코드만 허용한다.
- 기존 공통 속성: `environment`, `platform`, `app_version`

비밀번호, 토큰, 요청 본문, 원문 서버 메시지, 원문 파서 예외는 전송하지 않는다. API 예외 메시지는 메서드·정규화한 경로·오류 코드 또는 종류로 구성한다. 원문 예외를 그대로 전송하지 않으므로 값이 포함된 파서 메시지 대신 해당 API 파서와 서버 응답 계약을 대조해서 조사한다.

## Discord 알림과 수집은 별개다

현재 확인한 기존 Discord 알림은 `$error_tracking_issue_created`만 대상으로 한다. 같은 미해결 이슈의 발생이 추가되어도 새 이슈 생성이 아니므로 이 알림은 발송되지 않는다.

- 신규: 새 이슈 생성
- 해결 후 재발: 이전에 해결한 이슈가 다시 열림
- 급증: 기존 이슈의 발생량이 급증
- 매 발생: 이슈 상태와 무관하게 `$exception` 발생마다 보내는 별도 이벤트 목적지가 필요하다.

재발 알림 설정은 PostHog 프로젝트 설정이며 코드 배포만으로 바뀌지 않는다. 어떤 반복을 알릴지 확정한 뒤 기존 Discord 채널에 적용하고, 전송 실행 기록과 실제 채널 수신을 확인한다. 테스트용 알림은 테스트임을 표시하고 개인정보를 넣지 않는다. 등급은 수집을 막는 필터가 아니며 P2를 낮은 우선순위로 기록해도 알림 제외를 의미하지 않는다.

| 발견한 문제               | 확인한 내용                                                                                               | 대응                                                                                                           |
| ------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 체크리스트 오류 반복      | 운영 `GET /api/checklists?stage=ON_SITE`에서 HTTP 200 응답 처리 실패가 같은 이슈에 17회·6세션 묶여 있었다 | 실제 응답과 파서의 불일치는 별도 조사 필요. 세션 링크 없이는 사용자가 지적한 발생과 동일하다고 확정하지 않는다 |
| 신규 이슈만 Discord 전송  | 기존 트리거가 issue created이고 최근 실행은 성공했다                                                      | 재발 알림의 세부 기준을 확정 후 프로젝트 설정에서 적용                                                         |
| 4xx 수집 누락             | API 클라이언트가 모든 4xx를 전송하지 않았다                                                               | P2로 수집, 응답 계약 오류는 P1                                                                                 |
| 성공 envelope 수집 누락   | 200이어도 SUCCESS·message·data 형식 검증 실패가 수집 없이 throw됐다                                       | 공통 실패 경계로 통합                                                                                          |
| Blob 수집 누락            | 사진 등 Blob 요청의 실패가 공통 수집 경계를 거치지 않았다                                                 | JSON 요청과 동일하게 수집                                                                                      |
| 204 파서 실패 수집 누락   | 204의 parseData 예외가 수집 경계를 우회했다                                                               | 상태 코드와 함께 수집                                                                                          |
| API 쿼리에 위치 등이 남음 | 기존 request_path가 쿼리 전체를 포함했다                                                                  | 쿼리·숫자 ID·원문 예외 제거                                                                                    |

이 문서의 코드 보강은 로컬 작업 내용이다. 운영에 배포되기 전에는 기존 수집 누락이 남는다. SDK 미초기화, 차단, 네트워크 단절, SDK 로딩 실패 등에서는 전송 자체가 보장되지 않는다. `getPostHogDiagnostics`의 상태·실패·큐 누락 수를 함께 확인한다.

## 청크 오류 정책

청크 로딩 실패는 자동 수집과 라우트 오류 경계의 수동 수집 모두 `severity=P2`, `error_category=chunk_load`로 전송한다. `ChunkLoadError` 타입 또는 Webpack의 `Loading chunk … failed` / `Loading CSS chunk … failed` 메시지만 대상으로 삼으며, 다른 오류의 등급은 낮추지 않는다. 수집을 차단하지 않고 기존 새로고침 안내도 유지한다.

배포 시 이전 청크는 기존 정책대로 삭제한다. 등급 하향은 오류 복구나 청크 보존을 의미하지 않는다. 이번 API 수집 보강에서는 배포 삭제 정책을 변경하지 않는다. 보존 기간을 바꾸려면 별도로 기간과 정리 방법을 확정한다.

이벤트의 사용자 정의 `severity` 속성과 PostHog Error Tracking 이슈의 Low/Medium/High 등급은 별개다. 기존 이슈 등급과 알림 조건은 PostHog에서 별도로 관리한다. 이벤트 등급만 바꾸어도 기존 Discord 알림이 자동으로 꺼지는 것은 아니다.
