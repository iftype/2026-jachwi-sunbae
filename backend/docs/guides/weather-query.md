# 현재 위치 날씨 조회와 위치 동기화

EPIC 06의 백엔드 구현과 검증 방법을 설명한다. 공개 요청·응답 계약은 `WeatherForecastController`, `MemberWeatherLocationController`의 Swagger/OpenAPI에서 관리한다. 모바일 권한 요청·GPS 획득·WebView 전달·화면 연결은 후속 작업이다. EPIC 07의 백엔드 정기 알림과 24시간 위치 유효기간은 [정기 생활 날씨 알림](weather-notifications.md)에서 설명한다.

## 조회 흐름과 책임

1. 앱이 현재 위경도로 날씨 조회를 요청한다. 기존 익명 회원 Bearer 인증을 사용한다.
2. `KmaGridConverter`가 위경도를 기상청 격자로 변환한다.
3. `WeatherForecastQueryService`가 KST 오늘 또는 내일인지 검사한다. 날짜 생략 시 주입받은 `Clock`의 KST 오늘이다.
4. `WeatherForecastQueryRepository`가 해당 격자·날짜의 시간별 최대 24행과 일별 1행의 두 요소를 조회한다. 시간별 PK `(grid_x, grid_y, forecast_at)`와 일별 PK `(grid_x, grid_y, forecast_date)`를 사용한다. 완료 기록은 발표시각 PK로 조인한다.
5. 서비스가 각 값의 완료 여부·신선도·결측을 판단하고, 컨트롤러가 KST 오프셋 `+09:00`을 포함한 응답으로 변환한다.

예를 들어 서울 시청 좌표 `(37.5665, 126.978)`는 `(60, 127)`에 대응한다. 같은 격자로 변환되는 다른 위치도 동일한 DB 행을 읽는다. 조회 요청은 위치를 저장하지 않으며 외부 기상청 API를 호출하거나 전국 격자를 순회하지 않는다. 별도 캐시는 아직 없다.

정기 알림은 `WeatherForecastQueryService.findByGrid(grid, date)`를 재사용한다. 위치를 다시 위경도로 복원할 필요가 없다. 조회의 가용 상태만으로 발송을 결정하지 않고, 필요한 시간대·요소의 충족 여부와 알림용 위치 유효기간을 EPIC 07의 판정·발송 서비스에서 추가 검사한다.

## 좌표와 범위

[기상청 격자자료 안내](https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=286)의 공식 격자영역 자료에 제시된 Lambert conformal conic 투영을 사용한다. 지구 반경 6,371.00877km, 격자 간격 5km, 표준 위도 30°·60°, 기준점 `(38°N, 126°E) → (43, 136)`이다. 반올림한 격자는 X 1~~149, Y 1~~253 범위여야 한다.

`KmaGridConverterTest`는 공식 기준점·모서리와 서울·수원·부산·제주 샘플을 검사한다. 수원 시청 좌표 `(37.2636, 127.0286)`는 `(61, 120)`, 부산 시청 `(35.1796, 129.0756)`은 `(98, 76)`이다. RAW의 0 기반 인덱스는 `(ny - 1) * 149 + (nx - 1)`로 대조한다. 도시 샘플은 공식 투영식의 회귀 테스트이며 별도 실제 API 호출 결과와의 대조를 뜻하지 않는다.

NaN·무한대·잘못된 위경도는 입력 오류, 투영 후 격자 밖은 지원 지역 오류다. 경계로 강제 보정하지 않는다. 격자 범위 안이라는 이유로 육지나 서비스 가능한 지역이라고 단정하지 않는다. 바다 등 저장 행이 없는 격자는 조회 결과의 미수집 상태로 표현한다. 현재 데이터만으로 바다와 아직 수집하지 않은 육지의 원인을 구별하지 않는다.

## 날짜·신선도·값의 상태

오늘·내일 각각 00~23시의 24개 슬롯과 일별 TMN·TMX를 반환한다. 과거 날짜와 모레 이후는 오류다. 오늘 이미 지난 시각도 포함하며, 처음 수집하기 전의 시각은 빈 값으로 남는다. 내일 24시간을 포함하도록 수집 계획을 발표 다음 정시부터 **48시간**으로 확장했다. 요청 수·용량과 재현 명령은 [수집 가이드](weather-collection.md)를 따른다.

| 상태            | 의미                                                                                    |
| --------------- | --------------------------------------------------------------------------------------- |
| `AVAILABLE`     | 이번 수집 시도의 완료·신선도 검사를 통과한 수치. 정상 0과 음수 기온도 보존              |
| `MISSING`       | 완료·신선도 검사는 통과했지만 해당 격자·요소의 원본 값이 결측                           |
| `NOT_COLLECTED` | 조회할 저장 행 또는 해당 요소의 출처가 없음                                             |
| `NOT_PROVIDED`  | 당일 TMN·TMX 출처가 없고, 현재 선택할 발표분에서 해당 일별 요소를 더 이상 제공하지 않음 |
| `STALE`         | 해당 대상시각에 기대하는 발표분보다 6시간을 초과해 오래됨                               |
| `UNVERIFIED`    | 완료 기록이 없거나 진행·실패 중이거나 행의 수집시각이 완료된 시도의 범위에 속하지 않음  |

`AVAILABLE` 이외에는 수치를 `null`로 반환한다. 출처가 있으면 발표·수집시각은 유지한다. 응답 전체의 `coverage`는 194개 값(24시간 × 8요소 + 일별 2요소)이 모두 사용 가능하면 `AVAILABLE`, 일부면 `PARTIAL`, 하나도 없으면 `UNAVAILABLE`이다. `coverage`는 각 요소의 상태를 대체하지 않는다.

신선도 기준은 **초기 서비스 정책**이다. 현재 및 미래 시각에는 공개 대기시간을 적용한 최신 발표분을 기대한다. 과거 시간대는 당시까지 공개 가능한 발표분을 기준으로 삼는다. 6시간 차이는 허용하고 이를 넘으면 오래된 값으로 처리한다. 일별 TMN은 대상일 02시, TMX는 대상일 11시 발표에서 기대 시각을 멈춘다. 따라서 오후에도 정상 수집한 당일 최저기온을 단순히 수집 후 오래되었다는 이유로 버리지 않는다. 기상청 공개 지연 15분은 기존의 미검증 초기 설정을 그대로 사용한다.

TMN·TMX의 `NOT_PROVIDED`는 최신 발표의 제공 규칙을 나타낸다. 이전 발표에서 수집한 유효 값이 있으면 그것을 반환한다. 계획상 미제공과 정상 응답의 NULL 결측을 혼동하지 않는다.

모든 수치는 기존 RAW 저장 계약을 유지한다. 특히 POP·PCP·SNO는 의미와 비0 단위 대응이 아직 확인되지 않아 확률·mm·cm로 임의 변환하지 않는다. 사용자 화면이나 EPIC 07의 조건 판정에 쓰기 전 [RAW 계약 검증 기록](weather-raw-contract.md)을 확인해야 한다.

## 완료 기록과 기존 데이터

V4는 `weather_collection_publications`에 발표분별 최근 시도의 시작·완료시각(KST)을 저장한다. 수집 시작 시 완료시각을 비우고, 모든 시간별·일별 저장의 커밋 이후 완료시각을 쓴다. 행의 `collected_at`이 해당 시작·완료 사이에 있어야 조회에서 인정한다. 같은 발표분을 재시도해도 이전 시도에만 저장된 행을 이번 성공으로 오인하지 않는다.

기존 데이터에 성공 기록을 추측해서 채우지 않는다. V4 적용 전에 저장한 데이터는 `UNVERIFIED`이며, 명시적 수동 수집 또는 최초 적재가 필요하다. 완료가 확인되지 않는 행만 있다면 `--initialize`를 막지 않는다. 설정은 기존과 같이 기본 OFF이고 서버 재시작만으로 수집하지 않는다.

이 기록은 배치 전체 원자성을 제공하지 않는다. 실패 전 커밋한 행은 DB에 남지만 조회에서 수치가 숨겨진다. 기존 PK는 동일 대상시각의 최신 발표분만 보관하므로 실패한 신규 발표가 이전 행을 덮어썼다면 이전 성공값으로 돌아갈 수 없다. 원자적 교체·이력·재처리·다중 JVM의 중복 실행은 EPIC 05에서 다룬다. 완료 메타데이터는 과거 예보 삭제와 별개로 유지되며 하루 최대 8개 발표 키씩 늘어난다.

## 회원별 위치 동기화

`MemberWeatherLocationService`는 JWT의 회원 ID만 사용한다. 다른 회원을 지정하는 입력을 받지 않으며 기존 `MemberService`로 회원 존재를 확인한다. V5의 `member_weather_locations`는 회원별 한 행이고 회원 삭제 시 함께 삭제된다.

DB에는 격자, 실제 위치 확인시각(`location_observed_at`), 서버 반영시각(`synced_at`), 해제시각(`invalidated_at`)만 저장한다. 정확한 위경도는 변환 후 보관하지 않는다. 위치 시각은 UTC로 저장하고 응답은 ISO 8601 `Instant`로 표현한다. 예보의 KST 시각과 구분한다. 애플리케이션 요청 로그는 경로만 남기고 쿼리나 요청 본문을 기록하지 않는다. 배포 프록시에서도 위치 쿼리와 본문을 기록하지 않도록 해야 한다.

- 기기가 실제로 위치를 확인한 `observedAt`을 전달해야 한다. 캐시 재전송 시 현재 시각으로 바꾸면 안 된다.
- 초기 동기화 정책으로 서버 기준 최근 5분 이내의 확인시각과 최대 1분의 미래 기기 시각 오차를 허용한다. 이 기준은 EPIC 07의 알림용 위치 유효기간과 별개다.
- 같은 격자여도 새로 확인한 위치라면 갱신한다. 동일·이전 확인시각의 요청은 SQL 조건부 UPSERT로 무시하며 `syncedAt`도 갱신하지 않는다. 늦게 도착한 이전 위치가 최신 위치를 덮어쓰지 않는다.
- 해제 요청은 격자를 지우고 해제시각을 보존한다. 해제시각 이전의 위치 요청이 늦게 도착해도 다시 등록하지 않는다. 이후 실제로 새 위치를 획득하면 다시 동기화할 수 있다. 기기 시각은 서버가 허용한 오차 범위 안에서 신뢰한다.
- 위치 조회의 `available`은 등록 여부만 뜻한다. 앱을 오래 열지 않아 실제 위치가 바뀌었는지 서버가 알 수 없으며, 알림 직전에 반드시 별도 유효기간을 검사해야 한다.

예를 들어 12:00에 위치를 확인해 저장한 뒤 12:02에 같은 격자를 새로 확인하면 확인시각이 12:02로 바뀐다. 이후 12:00 요청이 재전송되어도 되돌아가지 않는다. 권한을 철회하면 앱이 해제 API를 호출해야 서버에 반영된다. 운영체제 권한 철회를 서버가 독립적으로 감지하지는 못한다.

## 검증과 후속 연결

`backend`에서 실행한다.

```bash
./gradlew test --tests '*weather.*' --tests '*DatabaseBaselineIntegrationTest' --no-daemon
```

- 좌표 변환: 공식 기준점·모서리, 지역 샘플, 동일 격자, RAW 인덱스, 잘못된 좌표.
- 조회 서비스: 오늘·내일, KST 연말 경계, 0·결측·미제공·오래됨·미완료, 시간별 및 일별 출처.
- MySQL API 통합: Flyway V4·V5, 해당 격자·날짜만 조회, JWT 권한, 위치 동기화·재전송·해제, 날짜 직렬화.
- 수집 통합: 48시간 요청·저장, 일별 날짜 확장, 실패 시 완료 기록을 남기지 않음, 완료 기록 없는 행의 최초 적재 판정.

테스트의 기상청 HTTP 응답은 모의 RAW다. 이번 작업에서 실제 기상청 48시간 전체 호출, Android/iOS 권한·GPS·WebView, 프론트 화면, FCM 발송은 검증하지 않았다. 앱 연결 시 권한 거부·위치 서비스 OFF·오래된 캐시·회원 인증 복원 실패를 포함한 인수 시나리오를 추가해야 한다.
