# 정기 생활 날씨 알림

EPIC 07의 백엔드 구현이다. 기존 익명 회원 JWT, 마지막 동기화 격자, MySQL의 완료된 예보를 사용한다. Firebase 인증으로 회원 체계를 바꾸지 않는다. HTTP 입력·응답 계약은 `WeatherNotificationSettingsController`, `WeatherNotificationHistoryController`의 Swagger/OpenAPI를 기준으로 한다. 앱의 권한 요청·FCM 등록정보 획득·알림 클릭 화면은 후속 작업이다.

## 동작 흐름

1. 앱이 기존 익명 인증으로 회원을 식별하고, EPIC 06의 위치 동기화로 격자와 실제 위치 확인시각을 보낸다.
2. 회원의 알림 수신 동의를 켜고, 설치별 FCM 토큰과 OS 알림 권한 상태를 등록한다. 회원 동의와 기기 권한은 서로 독립적이며 둘 다 허용되어야 한다.
3. KST 07:00에는 오늘 07~~23시, 22:00에는 내일 00~~23시를 분석한다. 정상 완료된 05시·20시 발표분 이상이 필요하며, 부족하면 해당 실행을 보류한다. 사용자마다 기상청을 다시 호출하지 않는다.
4. `WeatherNotificationPreparationService`가 당시 격자·확인시각·대상 날짜·원본 조회 결과·7가지 판정·문구·정책 버전을 하나의 스냅샷으로 저장한다. 알림과 대상 기기 목록은 같은 DB 트랜잭션으로 생성된다.
5. `WeatherNotificationDispatchService`가 발송 직전에 동의, 위치, 기기 소유자와 등록 버전을 다시 검사하고 기기별 발송권을 얻는다. DB 트랜잭션을 끝낸 뒤 FCM을 호출한다.
6. 앱은 푸시의 `data.notificationId`로 본인 알림 상세를 조회한다. 이 응답은 현재 위치나 새 예보로 다시 계산하지 않는다. 실제 기기 수신·열람은 별도 보고 API로 기록한다.

예를 들어 06:50 서울에서 위치를 확인한 회원은 07:00에 서울 격자의 오늘 예보를 받는다. 14:00 부산에서 다시 위치를 동기화했다면 22:00 알림은 부산의 내일 예보를 사용한다. 이때 오전 알림을 열면 서울의 오전 발송 준비 당시 예보를 보여준다. 앱을 열지 않고 이동한 경우 서버가 그 이동을 알아낼 수는 없다.

## 시간·위치·자료 정책

| 항목           | 초기 정책                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 기준 시간대    | `Asia/Seoul`                                                                                           |
| MORNING        | 발송일의 07~23시, 같은 날 05시 발표분 이상                                                             |
| EVENING        | 발송 다음 날 00~23시, 발송일 20시 발표분 이상                                                          |
| 실행·재시도 창 | 07:00~~07:59, 22:00~~22:59. 해당 시간 안에서 5분마다 검사                                              |
| 위치 유효기간  | 실제 `observedAt`부터 24시간 이내, 최대 1분 미래 시각 오차 허용                                        |
| 필수 예보      | 대상 시간 전체의 TMP·PTY가 완료·최신·정상 범위여야 발송                                                |
| 선택 예보      | 요소별 결측·미제공·해석 미확정은 해당 판정을 `UNKNOWN`으로 표시                                        |
| 일별 기온      | 조회 서비스가 판정한 정상 TMN·TMX 사용. 제공 시각이 다른 일별 값에 시간별 05/20시 조건을 강제하지 않음 |
| 지연 도착      | Android TTL과 APNs 만료를 각각 08:00·23:00에 맞춤. 실제 도착 시각 보장은 아님                          |

24시간은 이용 패턴 실측 전의 초기 정책이다. `syncedAt`을 위치 확인시각으로 대신 쓰지 않는다. 24시간이 정확히 지난 경계는 허용하고 초과하면 보류한다. 위치 해제나 격자 변경 후에는 이미 준비했더라도 아직 발송하지 않은 기존 지역의 알림을 보내지 않는다.

정기 알림은 수집 서비스의 성공 여부만 믿지 않고 EPIC 06 조회의 요소별 상태와 발표시각을 검사한다. 이전 발표분으로 자동 대체하지 않는 보수적 정책이다. 준비하지 못한 알림은 같은 시간대의 다음 검사에서 재평가하지만, 이미 준비한 알림은 같은 스냅샷을 사용한다. 스케줄러는 수집·삭제 스케줄러와 별도 스레드에서 실행되며, 서버 시작 직후 즉시 발송하거나 지난 슬롯을 소급 발송하지 않는다.

## 7가지 판정과 문구

`LifeWeatherRules`는 DB·HTTP·시계에 의존하지 않는 순수 규칙이다. 아래 `life-weather-v1` 임계값은 공식 기상특보 기준이 아닌 **초기 생활 안내 가설**이며, 실제 비·눈·극한 기온 자료 및 사용자 경험으로 보정해야 한다.

| 항목        | 초기 조건                                                      | 결측·주의점                                                             |
| ----------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 비          | PTY 1·2·4, 또는 검증된 PCP 양수·POP 60% 이상                   | 확률 문구에 해당 예보시각 명시                                          |
| 눈          | PTY 2·3, 또는 검증된 SNO 양수                                  | 비와 눈이 섞이면 둘 다 주의 가능                                        |
| 수도관 보온 | 시간별 TMP 또는 일별 TMN이 -5℃ 이하                            | 실제 주택 동파 확정이 아닌 보온 점검 안내                               |
| 일교차      | 정상 일별 TMX − TMN이 10℃ 이상                                 | 남은 시간별 기온의 최저·최고를 일 최저·최고로 대체하지 않음             |
| 건조        | 대상 시간 중 REH 35% 이하                                      | 실내 습도를 확인하라는 안내이며 공식 건조특보 아님                      |
| 빨래        | 09~~18시 모두 PTY·PCP·SNO 0, POP ≤30, REH ≤60, WSD 1~~7        | 낮에 PTY 강수가 있으면 실내 건조 고려. 추천은 모든 필요 값 검증 후 가능 |
| 환기        | 10~~17시 중 PTY·PCP·SNO 0, REH 40~~70, WSD ≤5, TMP 5~28인 시각 | 실외 공기질을 별도로 확인한 뒤 고려하도록 안내                          |

정상 0과 결측은 구분한다. 기온·습도·풍속·PTY의 정상 범위를 벗어나거나 무한대/NaN인 값도 판단에 쓰지 않는다. 충분한 경고 근거가 하나 있으면 주의를 안내할 수 있지만, 자료가 빠졌다는 이유로 “비 없음”이나 “추천”으로 바꾸지 않는다.

주의 우선순위는 눈 → 비 → 수도관 보온 → 일교차 → 건조 → 빨래다. 제목에 주의 1개, 본문에 추가 주의 최대 1개를 넣는다. 주의가 없으면 빨래·환기 추천, 그것도 없으면 해당 시간 구간의 예보기온 요약을 제공한다. 7개 판정은 상세에 모두 보존한다. 상태는 `CAUTION`, `RECOMMENDED`, `NOT_APPLICABLE`, `UNKNOWN`이다.

### RAW 해석의 미확정 부분

[기존 RAW 검증](weather-raw-contract.md)에서 POP·PCP·SNO의 의미와 비0 응답 대응이 미확정이다. [기상청 API허브](https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=286)의 POP 표기도 확인이 필요하다. 이에 따라 `WEATHER_PRECIPITATION_CONTRACT_VERIFIED`는 기본 `false`다.

- OFF: PTY로 확인되는 비·눈은 주의 판정한다. 나머지 POP·PCP·SNO 해석이 필요한 비·눈 부정 판정과 빨래·환기 추천은 `UNKNOWN`으로 남긴다. 기온·일교차·건조 규칙은 사용할 수 있다.
- ON: 검증된 POP 퍼센트, PCP·SNO의 정상 0/양수 계약을 전제로 전체 규칙을 적용한다. 단순히 추천을 보이게 하려고 켜는 설정이 아니다. 실제 비0 RAW와 공식 의미를 대조하고 계약 문서를 갱신한 뒤 활성화한다.

테스트는 저장된 실제 2026-10-22 20시 서울 격자 샘플을 읽어 미확정 값을 단정하지 않는지 확인한다. 전체 시간대와 양수·임계값 테스트는 합성 자료다. 하루 전체의 실제 비·눈 자료 검증이나 임계값의 실서비스 적절성 검증을 완료한 것은 아니다.

## 기기 등록과 익명 회원 변경

앱 설치마다 무작위 UUID `installationId`와 충분히 무작위인 비밀키 `installationSecret`을 만든다. 비밀키는 최소 32바이트 난수를 Base64url로 인코딩한 43~128자이며 서버에는 SHA-256 해시만 저장한다. 서버는 난수의 품질까지 확인할 수 없으므로 앱에서 안전한 난수 생성기를 사용한다. 두 값은 익명 JWT 초기화와 별도로 보존해야 한다.

- 인증된 회원만 자신의 동의·기기를 조회하고 해지한다. 응답에는 FCM 토큰·설치 비밀키·해시를 포함하지 않는다.
- 같은 설치의 토큰·권한 변경이나 새 익명 회원으로의 이전에는 설치 비밀키 증명이 필요하다. UUID를 안다는 이유만으로 기기를 가져갈 수 없다.
- 회원이 바뀌어도 설치 증명을 유지하면 동일 기기를 새 회원으로 이전할 수 있다. 이전 회원의 연결은 제거되고 수신 동의는 새 회원의 별도 설정을 따른다.
- 동일 토큰을 여러 설치에 중복 등록하지 못한다. 설치 증명을 잃은 앱은 기존 등록을 해지할 수 있을 때 먼저 해지하거나 새로운 FCM 토큰을 발급받아 등록한다.
- OS 권한 `DENIED` 또는 기기 해지는 토큰을 지우고 비활성화한다. OS 권한은 앱이 보고한 상태이므로, 서버가 기기 설정을 직접 확인하는 것은 아니다.
- 등록 내용이 같으면 버전을 유지하고, 토큰·권한·회원이 바뀌면 버전을 올린다. 준비 이후 등록이 변경된 기기는 그 슬롯의 기존 발송을 취소한다. 새 등록은 다음 슬롯부터 반영한다.
- 앱은 익명 회원 변경 시 새 등록 완료 전에 알림 처리를 재개하지 않고, 현재 회원이 접근할 수 없는 알림 상세를 표시하지 않아야 한다. 이미 FCM에 전달한 알림을 서버가 회수할 수는 없다.

회원당 활성 기기 등록은 기본 10개까지 허용한다. 등록 API는 JWT 소유권과 설치 증명을 함께 검사하며, Firebase 로그인이나 사용자의 정확한 위경도를 요구하지 않는다.

## 발송 기록과 실패 정책

V6 마이그레이션이 회원 동의, 기기 등록, 알림 스냅샷, 기기별 전송의 네 테이블을 추가한다. 날짜·예보시각은 KST 계약을 따르고, 위치 확인·발송·수신 Instant는 UTC `DATETIME(6)`으로 저장한다. 스냅샷은 이후 예보 테이블 정리와 무관하게 남는다. 보존 기간·별도 이력 정리는 후속 운영 정책으로 결정해야 한다.

회원 × 발송일 × 슬롯의 DB 유니크 키로 논리적 알림을 한 번 생성한다. 알림 × 설치의 PK와 조건부 UPDATE로 `PENDING/RETRY → SENDING` 발송권을 한 작업만 획득한다. 단일 인스턴스에서는 실행 중첩도 막는다. 같은 회원의 여러 기기에는 각각 한 번씩 발송할 수 있다.

| 상태        | 의미와 다음 처리                                                                         |
| ----------- | ---------------------------------------------------------------------------------------- |
| `PENDING`   | 스냅샷·대상 기기 저장 완료, 아직 요청 전                                                 |
| `SENDING`   | 발송권 확보 후 FCM 요청 중                                                               |
| `ACCEPTED`  | FCM 요청 수락, 휴대폰 도착 확인과 구분                                                   |
| `RETRY`     | QUOTA_EXCEEDED. 기본 5분 또는 Retry-After 대기 후 슬롯 내 최대 총 3회 시도               |
| `FAILED`    | 잘못된 요청·등록 만료·재시도 한도/만료 도달. UNREGISTERED는 해당 등록 버전만 비활성화    |
| `UNKNOWN`   | 서버 오류·응답 유실 등 결과 불명. 중복 방지를 위해 애플리케이션에서 자동 재전송하지 않음 |
| `CANCELLED` | 동의·위치·기기 조건 변경 또는 슬롯 만료                                                  |

프로세스가 발송권 확보 후 중단되어 5분 이상 `SENDING`으로 남은 기록은 다음 작업에서 `UNKNOWN`으로 전환한다. 만료된 `PENDING/RETRY`도 다음 작업에서 취소한다. 이 정책은 불확실한 전송의 중복보다 누락 가능성을 선택한다. 다중 서버 부하·장애 복구 전체를 검증한 운영 보장은 아니다.

FCM 수락과 모바일 도착은 다르며 [Firebase SDK 내부 재시도](https://firebase.google.com/docs/reference/admin/error-handling)와 네트워크 때문에 **기기에 정확히 한 번 도착하는 것을 보장하지 않는다**. 애플리케이션은 수락·결과 불명 건을 다시 요청하지 않는다. 동일 notificationId를 Android tag/collapse key와 APNs collapse ID로 사용해 중복 표시를 줄이고, 모바일도 같은 ID를 기준으로 처리해야 한다. [TTL](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)은 뒤늦은 전송을 제한한다.

수신·열람 보고 API는 서버가 최초 보고시각을 보존하며 재전송에 멱등적이다. `OPENED`는 수신도 포함하고, 이후 `RECEIVED` 보고가 열람 기록을 지우지 않는다. 이 시각은 클라이언트 보고이지 서버가 직접 관찰한 OS 도착시각이 아니다. 발송 로그에는 notificationId·시도 횟수·결과 코드·전체 처리 시간을 남기며 토큰·설치 비밀키·좌표·FCM 예외 본문을 출력하지 않는다.

## 설정과 검증

```dotenv
WEATHER_NOTIFICATION_ENABLED=false
WEATHER_PRECIPITATION_CONTRACT_VERIFIED=false
WEATHER_FIREBASE_PROJECT_ID=
```

기본 OFF에서는 Firebase 자격증명이 필요 없으며 스케줄러를 등록하지 않는다. 회원 설정·기기 등록·이력 API는 사용할 수 있다. 수집·초기 적재·정리 플래그와 독립적이다.

ON으로 실행하려면 Firebase 프로젝트 ID와 Google Application Default Credentials를 실행 환경에 제공한다. 지원 환경의 워크로드 자격증명을 우선 사용하고, 파일 방식이면 `GOOGLE_APPLICATION_CREDENTIALS`에 저장소 밖 자격증명 파일 경로를 지정한다. 실제 키 파일·토큰을 Git이나 로그에 넣지 않는다. Firebase Admin SDK 9.11.0을 사용하며, 이번 계약은 FCM 등록 토큰 기반이다. 해당 SDK의 토큰 API는 deprecated이므로 모바일 연결 시 FID 전환과 호환성도 검토한다. [Admin Java 변경 기록](https://firebase.google.com/support/release-notes/admin/java)을 참고한다.

외부 FCM 호출 없이 테스트하려면 Docker를 실행한 뒤 `backend`에서 다음을 실행한다.

```bash
./gradlew test --tests 'com.jachwisunbae.weather.notification.*'
./gradlew clean build
./gradlew testAll
```

순수 규칙, 실제 저장 샘플의 보수적 해석, KST 연말 경계, 설정 OFF/ON, FCM 요청 형식·만료·실패 분류, MySQL 등록·이전·동의 철회·조회 권한·스냅샷·동시 발송권·재실행·중단 복구·재시도 한도·수신 보고를 검증한다. 테스트에서 FCM은 대역으로 교체하고 실제 푸시는 보내지 않는다.

모바일 연동 때 Firebase 프로젝트 및 Android/iOS 설정, OS 권한 거부·복구, 토큰 갱신, 익명 회원 초기화, 백그라운드 수신, 클릭 시 JWT와 상세 조회, notificationId 중복 처리, 실제 오전·저녁 도착과 오래된 위치 안내를 실제 기기로 확인해야 한다. EPIC 05의 수집 실패 복구와 실제 RAW 비·눈 계약 검증도 운영 활성화 전에 이어서 수행한다.
