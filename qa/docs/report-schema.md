# QA 실행 결과 형식

- 상태: v0.1 / 작성일: 2026-10-06

Scenario를 한 번 실행한 결과(Run Report)를 어떤 구조로 기록할지 정한다. 수동 실행과 자동 실행 모두 같은 형식을 쓴다.

## 1. 구성 원칙

Run Report는 공통 뼈대에 Scenario별 내용을 채워 만든다.

| 구분            | 정하는 곳                          | 내용                                                          |
| --------------- | ---------------------------------- | ------------------------------------------------------------- |
| 공통 뼈대       | 이 문서                            | 실행 정보, Expected별 결과, Evidence 목록, AI 분석, 사람 판정 |
| Scenario별 내용 | 각 [Scenario](scenarios/README.md) | Expected, Required Evidence, 판정 메모                        |

실행 결과(코드 및 AI의 판정)와 사람 판정은 항상 구분해 기록한다. AI 분석은 사람 확인 전까지 초안이다.

## 2. Run Report 구조

### 2.1. 실행 정보

| 필드                | 내용                                                                           |
| ------------------- | ------------------------------------------------------------------------------ |
| Run ID              | `{Scenario ID}-{runId}`. 예: `F02-S01-261006-143015`                           |
| Scenario            | Scenario ID와 실행 당시 상태                                                   |
| 환경                | 실행 환경과 URL                                                                |
| 대상 버전           | 실행 대상 백엔드의 버전과 커밋(DEV `/actuator/info`). 알 수 없으면 `확인 불가` |
| 실행 방식           | `수동` 또는 `자동`. 실행자(사람) 또는 실행 도구와 버전                         |
| 시작 시각·소요 시간 | 실행 시작 시각과 전체 소요 시간                                                |
| 테스트 데이터       | 사용한 닉네임, 생성된 자원 ID 등                                               |

### 2.2. 결과 요약

- 최종 판정: [판정 규칙](#4-판정)에 따라 Expected별 판정을 집계한 값
- 한 줄 요약: 무엇이 확인됐고 무엇이 문제인지

### 2.3. Expected별 결과

| 열        | 내용                                                                                                              |
| --------- | ----------------------------------------------------------------------------------------------------------------- |
| ID        | Scenario의 Expected ID                                                                                            |
| 기대 결과 | Scenario의 기대 결과 요약                                                                                         |
| 근거      | Scenario Expected의 근거 명세 ID                                                                                  |
| 실제 결과 | 관찰한 사실. 해석을 섞지 않는다.                                                                                  |
| 판정      | `PASS` · `FAIL` · `NEEDS_REVIEW` · `BLOCKED`. 코드가 `NEEDS_REVIEW`로 넘긴 Expected는 AI 판정 초안을 함께 적는다. |
| 판정 주체 | `코드` · `AI` · `사람`                                                                                            |
| Evidence  | 근거 Evidence ID                                                                                                  |

### 2.4. Evidence 목록

| 열   | 내용                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------ |
| ID   | Scenario의 Evidence ID. Scenario 밖에서 수집한 Evidence(마지막 화면, 실패 시 추가 수집)는 `EV+1`부터 붙인다. |
| 종류 | 스크린샷, API, 콘솔, 네트워크, 기록, 트레이스, 서버 로그                                                     |
| 위치 | 파일 경로 또는 링크                                                                                          |
| 설명 | 무엇을 보여주는지 한 줄                                                                                      |

### 2.5. 기타 관찰

Expected 밖에서 발견한 이상을 적는다. 판정하지 않고 사람에게 넘긴다. 없으면 `없음`이라고 쓴다.

### 2.6. AI 분석

최종 판정이 `FAIL`·`NEEDS_REVIEW`·`BLOCKED`일 때 작성한다. `PASS`인 Run도 기타 관찰을 찾기 위해 분석할 수 있다.

| 필드               | 내용                                                                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 문제 요약          | 사용자 관점에서 무엇이 잘못됐는지                                                                                                                   |
| 관련 근거          | 위반했거나 판단이 필요한 명세 ID                                                                                                                    |
| 원인 가설          | 가능한 원인과 각 가설을 뒷받침하는 Evidence ID. 여러 개 가능                                                                                        |
| 제안 심각도        | [심각도](#5-심각도) 등급과 이유. 결함이 아니라고 보면 `NONE`                                                                                        |
| 확신도             | `높음` · `중간` · `낮음`                                                                                                                            |
| 판정 제안          | AI가 예상하는 [사람 판정값](#44-사람-판정값)과 이유. 사람 판정과 비교해 AI 판단 품질을 잰다                                                         |
| Expected 판정 초안 | 코드가 `NEEDS_REVIEW`로 넘긴 Expected의 판정 초안, Evidence ID, 사람이 확인할 방법                                                                  |
| 기타 관찰          | Expected 밖에서 Evidence와 명세가 다른 점. 근거 명세 ID, Evidence ID, 판정 제안, 심각도 제안, 사람이 확인할 방법을 함께 쓴다                        |
| 추가 확인 제안     | 가설을 가리기 위해 더 볼 Evidence나 재현 방법                                                                                                       |
| 인용 검증          | AI가 인용한 명세 ID와 Evidence ID 중 실제로 없는 것, Evidence 없이 쓴 주장 수. 코드가 확인한다. 근거 칸과 Evidence 칸은 출력 형식에서 ID만 허용한다 |

AI 분석의 입력(보낸 프롬프트 원문)과 사용 모델을 Run 디렉터리에 함께 남겨, 사람이 AI가 무엇을 보고 판단했는지 확인할 수 있게 한다.

### 2.7. 사람 판정

사람 판정은 Run 판정과 항목별 판단 두 표로 나눈다. 한 Run에서 AI가 여러 주장을 내므로, Run 전체의 판정과 주장 하나하나에 대한 판단을 따로 남긴다.

**Run 판정**: Run 전체의 결함 여부. AI 판단은 판정 제안과 원인 가설에 대한 판단이다.

| 필드        | 내용                                                  |
| ----------- | ----------------------------------------------------- |
| 판정        | [사람 판정값](#44-사람-판정값)                        |
| 최종 심각도 | 사람이 확정한 등급. 결함이 아니면 비운다.             |
| AI 판단     | `수용` · `수정` · `기각`                              |
| 조치        | 버그 이슈, Scenario 수정, 명세 논의, 재실행 등과 링크 |
| 판정자·일시 |                                                       |

**항목별 판단**: AI가 낸 Expected 판정 초안과 기타 관찰마다 한 줄씩 판단한다. 항목별 AI 판단을 모으면 AI 판단 수용 비율을 항목 단위로 셀 수 있다.

| 열             | 내용                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 항목           | `Expected E2 판정 초안`, `기타 관찰 1`처럼 AI가 낸 주장                                            |
| AI 제안과 정리 | AI의 판정과 심각도 제안, 내용 정리, 근거 명세 ID, Evidence ID, 사람이 확인할 방법. 자동으로 채운다 |
| AI 판단        | `수용` · `수정` · `기각`                                                                           |
| 판정           | Expected 판정 초안이면 `PASS` · `FAIL` · `NEEDS_REVIEW`, 기타 관찰이면 사람 판정값                 |
| 최종 심각도    | 결함이면 사람이 확정한 등급                                                                        |
| 조치           | 버그 이슈, 코드나 Scenario 수정, 판단 기록 등                                                      |

최종 판정이 `PASS`인 Run은 결함 여부를 판정할 대상이 없다. 판정, 최종 심각도, AI 판단은 비우고, 조치에 `코드 판정 PASS 확인`을, 판정자·일시를 적는다. 사람이 결과와 Evidence를 확인했다는 기록이다.

사람 판정은 생성된 `report.md`에서 직접 채운다. 리포트를 다시 만들어도 채운 값은 유지된다. 단, AI 분석을 다시 하면 같은 항목 이름이 다른 주장을 가리킬 수 있어 항목별 판단은 옮기지 않는다. AI 판단이 `수정` 또는 `기각`이면 [판단 기록](decision-log/README.md)을 남긴다.

## 3. Evidence

### 3.1. 수집 계층

| 계층          | 언제                            | 내용                                                                          |
| ------------- | ------------------------------- | ----------------------------------------------------------------------------- |
| 항상          | 모든 실행                       | 실행 정보, Expected별 결과, 마지막 화면 스크린샷                              |
| Scenario 지정 | 모든 실행                       | Scenario의 Required Evidence                                                  |
| 실패 시 추가  | `FAIL`·`NEEDS_REVIEW`·`BLOCKED` | 브라우저 콘솔, 네트워크 기록(API와 문서 요청, 실패한 요청), 브라우저 트레이스 |

목표는 Evidence를 많이 모으는 것이 아니라 판정에 필요한 Evidence를 충분히 모으는 것이다.

API Evidence와 네트워크 기록에는 응답 헤더의 요청 ID(`X-Request-Id`)를 남긴다. 서버 로그는 자동으로 수집하지 않고, 필요하면 요청 ID로 찾는다.

### 3.2. 보관

- Run마다 `qa/runs/{Run ID}/`에 실행 결과(`result.json`)와 Evidence(`evidence/`)를 저장한다. Git에 커밋하지 않는다.
- 비밀번호, 인증 토큰, 쿠키는 Evidence에 남기지 않거나 가린다.

## 4. 판정

### 4.1. Expected 판정값

| 판정           | 의미                                                                            |
| -------------- | ------------------------------------------------------------------------------- |
| `PASS`         | 실제 결과가 기대 결과를 만족하고 Evidence로 확인된다.                           |
| `FAIL`         | 실제 결과가 명세와 다르고, 위반한 명세 ID를 지목할 수 있다.                     |
| `NEEDS_REVIEW` | 명세가 정하지 않았거나 미정 영역이다. 또는 해석이 갈리거나 Evidence가 부족하다. |
| `BLOCKED`      | 사전 조건 실패, 환경·외부 서비스 장애로 확인하지 못했다.                        |

판정 근거의 기준은 [QA 정답 기준](source-of-truth.md#3-판정-규칙)을 따른다.

### 4.2. 최종 판정

Expected별 판정 중 가장 앞선 값을 최종 판정으로 한다. 사람이 먼저 봐야 할 결과를 앞에 둔다.

```text
FAIL > NEEDS_REVIEW > BLOCKED > PASS
```

### 4.3. AI 확신도

| 확신도 | 기준                                    |
| ------ | --------------------------------------- |
| 높음   | Evidence가 문제와 원인을 직접 보여준다. |
| 중간   | Evidence와 맞지만 다른 설명도 가능하다. |
| 낮음   | 추가 Evidence 없이는 판단하기 어렵다.   |

AI가 내는 숫자 확신도(예: 0.82)는 보정되지 않아 숫자 사이의 차이에 의미가 없으므로 세 단계로만 기록한다.

### 4.4. 사람 판정값

| 판정            | 의미                                      | 후속 조치                         |
| --------------- | ----------------------------------------- | --------------------------------- |
| `CONFIRMED_BUG` | 명세를 위반한 제품 결함                   | 버그 이슈 생성                    |
| `NOT_A_BUG`     | 명세상 정상. 코드나 AI의 판정 오류        | 판단 기록, 필요하면 Scenario 수정 |
| `SPEC_GAP`      | 명세가 정하지 않았거나 모호하다           | 제품 논의 후 명세 수정            |
| `TEST_ISSUE`    | Scenario·자동화 코드·테스트 데이터의 문제 | Scenario 또는 코드 수정           |
| `ENV_ISSUE`     | DEV 환경이나 외부 서비스 장애             | 재실행                            |

## 5. 심각도

AI는 이 기준으로 제안 심각도를 내고, 사람이 영향 범위를 고려해 최종 심각도를 정한다. 핵심 흐름은 F01 시작, F02 등록, F03 조회, F06 체크 기록이다.

| 등급     | 기준                                                                    | 예                                                                                                                      | 출시 판단                        |
| -------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| CRITICAL | 보안·개인정보 침해, 다른 회원 기록의 노출·변경, 사용자 기록의 대량 손상 | 다른 회원의 매물·사진 조회(`REQ-AUTH-007`), 보호된 닉네임의 비밀번호 우회(`REQ-AUTH-004`)                               | 출시 차단                        |
| HIGH     | 핵심 흐름을 수행할 수 없거나 저장한 데이터가 유실·왜곡된다              | 매물 등록 불가, 새로고침 후 매물이 사라짐, 금액이 다르게 저장됨, 체크 상태가 저장되지 않음, PDF에 다른 매물 기록이 섞임 | 기본 차단. 사람이 예외 승인 가능 |
| MEDIUM   | 기능 일부가 잘못되지만 목적을 달성할 우회 방법이 있다                   | 대표 사진 변경 실패, 한 시설 카테고리 조회 실패, 저장된 상태는 맞지만 집계 표시가 틀림                                  | 출시 가능. 다음 릴리스 전 수정   |
| LOW      | 기능 정확성에 거의 영향이 없다                                          | 문구 오탈자, 경미한 레이아웃 깨짐                                                                                       | 백로그                           |

## 6. 작성 예시

`QA_FAULT=detail-rent`로 의도적 결함을 주입해 F02-S01을 실행하고 자동 생성한 Run Report다. 사람 판정 칸은 비어 있는 상태다.

```markdown
# Run Report F02-S01-261007-095253

> **의도적 결함 주입 Run이다.** `detail-rent`: 매물 상세 조회 응답(GET /api/properties/{id})의 월세를 실제 값의 1/10로 바꾼다. 실제 제품 결함이 아니다. AI 분석에는 이 사실을 알리지 않았다.

## 실행 정보

| 필드 | 내용 |
| --- | --- |
| Run ID | F02-S01-261007-095253 |
| Scenario | [F02-S01 정상 매물 등록 후 재조회](../../docs/scenarios/F02-S01-property-create.md) (자동화) |
| 환경 | DEV, https://dev.jachwi-sunbae.kr |
| 대상 버전 | 확인 불가 |
| 실행 방식 | 자동, Playwright 1.63.0 |
| 시작 시각·소요 시간 | 2026-10-07 09:52:53 (KST), 8초 |
| 테스트 데이터 | 닉네임 qa-261007-095253, 회원 ID 44 |

## 결과 요약

- 최종 판정: **FAIL** (코드 판정)
- 한 줄 요약: 월세 50만원(500000원)으로 등록했지만 매물 상세에는 월세가 5만원으로 나온다. 생성 응답과 목록은 50만원이다. 상세 조회 API가 monthlyRentAmount를 50000으로 돌려주고, 등록 직후와 새로고침 후 모두 5만원으로 보인다. 이름과 보증금 500만원은 맞게 나온다.
```
