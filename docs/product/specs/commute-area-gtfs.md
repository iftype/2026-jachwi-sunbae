# 생활권 탐색 GTFS 데이터 구조와 파싱

- 상태: 검토용 초안 v0.1 / 작성일: 2026-10-10 / 대상: 스프린트 2

[생활권 탐색 명세](commute-area.md)의 `POL-COMMUTE-001`~`008`이 원천 데이터에서 어떻게 계산되는지 설명한다. 정책이 타당한지 사람이 판단할 수 있도록, KTDB 대중교통 GTFS 2025년 3월 데이터셋의 실제 행과 건수를 함께 적는다.

## 1. GTFS 개요

GTFS(General Transit Feed Specification)는 대중교통 시간표를 여러 개의 CSV 파일로 나눠 담는 표준 형식이다. 파일 확장자는 `.txt`지만 내용은 첫 줄이 헤더인 CSV다.

파일끼리는 ID로 이어진다.

```text
routes.txt ──route_id──▶ trips.txt ──trip_id──▶ stop_times.txt ──stop_id──▶ stops.txt
 (노선)                   (운행편)                (정차 기록)                    (정류장)
                                                                transfers.txt ──from/to_stop_id──┘
                                                                 (환승)
```

- 노선(route): 버스 100번, 지하철 2호선 같은 단위다.
- 운행편(trip): 노선이 하루에 실제로 한 번 달리는 것이다. 100번 버스의 04:00 첫차가 운행편 하나다.
- 정차 기록(stop_time): 운행편이 어느 정류장에 몇 시에 도착·출발하는지를 정류장마다 한 줄씩 적은 것이다.

## 2. 파일별 구조

KTDB 데이터셋은 파일 7개로 구성된다. 적재는 그중 5개만 읽는다.

| 파일             |      행 수 | 읽는가    | 용도                                  |
| ---------------- | ---------: | --------- | ------------------------------------- |
| `agency.txt`     |          - | 읽지 않음 | 운영 기관                             |
| `calendar.txt`   |          - | 읽지 않음 | 운행 요일 (`service_id`)              |
| `routes.txt`     |     26,399 | 읽음      | 노선과 교통수단 구분                  |
| `trips.txt`      |    326,368 | 읽음      | 운행편이 속한 노선                    |
| `stop_times.txt` | 18,889,140 | 읽음      | 구간 이동 시간과 배차 간격 (약 1.4GB) |
| `stops.txt`      |    215,409 | 읽음      | 정류장 이름과 좌표                    |
| `transfers.txt`  |        342 | 읽음      | 정류장 간 도보 환승 시간              |

### 2.1. routes.txt

```csv
route_id,agency_id,route_short_name,route_long_name,route_type
BR_TAGO_SEB100100549,A1,100,-,0
```

| 컬럼               | 사용 | 설명                                 |
| ------------------ | ---- | ------------------------------------ |
| `route_id`         | 사용 | 노선 ID                              |
| `agency_id`        | 무시 | 운영 기관                            |
| `route_short_name` | 사용 | 노선 번호 (`100`)                    |
| `route_long_name`  | 사용 | 노선 이름. KTDB 버스는 대부분 `-`다. |
| `route_type`       | 사용 | 교통수단 구분. 아래 표 참고          |

`route_type`의 분포와 적재 여부는 다음과 같다. GTFS 표준에서 `0`은 노면전차지만, KTDB 데이터는 일반 버스 대부분에 `0`을 쓴다.

| `route_type` | 표준 의미                  | KTDB 건수 | 적재 |
| ------------ | -------------------------- | --------: | ---- |
| 0            | 노면전차 (KTDB에서는 버스) |    23,858 | 적재 |
| 1            | 지하철·도시철도            |        91 | 적재 |
| 2            | 일반철도                   |       213 | 제외 |
| 3            | 버스                       |     1,864 | 적재 |
| 4            | 해운                       |        65 | 제외 |
| 5            | 케이블카                   |       219 | 제외 |
| 6            | 곤돌라                     |        53 | 제외 |
| 7            | 푸니쿨라                   |        36 | 제외 |

적재 대상은 `0`, `1`, `3`의 25,813개 노선이다 (`POL-COMMUTE-001`). 5~7은 표준 의미와 다르게 쓰였을 수 있지만, 건수가 적고 통근 수단으로 보기 어려워 의미를 확인하지 않고 제외했다.

### 2.2. trips.txt

```csv
route_id,service_id,trip_id
BR_TAGO_SEB100100549,B1,BR_TAGO_SEB100100549_Ord001
BR_TAGO_SEB100100549,B1,BR_TAGO_SEB100100549_Ord002
```

| 컬럼         | 사용 | 설명                                        |
| ------------ | ---- | ------------------------------------------- |
| `route_id`   | 사용 | 운행편이 속한 노선                          |
| `service_id` | 무시 | 운행 요일. `calendar.txt`와 이어진다.       |
| `trip_id`    | 사용 | 운행편 ID. `<route_id>_Ord<순번>` 형식이다. |

`service_id`를 무시하므로 평일·주말 운행편을 구분하지 않고 모두 합쳐 계산한다.

### 2.3. stop_times.txt

```csv
trip_id,arrival_time,departure_time,stop_id,stop_sequence,pickup_type,drop_off_type,timepoint
BR_TAGO_SEB100100549_Ord001,04:00:00,04:00:10,BS_TAGO_SEB110000327,1,0,0,1
BR_TAGO_SEB100100549_Ord001,04:00:24,04:00:34,BS_TAGO_SEB110000286,2,0,0,1
BR_TAGO_SEB100100549_Ord001,04:00:59,04:01:09,BS_TAGO_SEB110000273,3,0,0,1
BR_TAGO_SEB100100549_Ord001,04:01:49,04:01:59,BS_TAGO_SEB110000272,4,0,0,1
```

| 컬럼                           | 사용 | 설명                                                        |
| ------------------------------ | ---- | ----------------------------------------------------------- |
| `trip_id`                      | 사용 | 운행편                                                      |
| `arrival_time`                 | 사용 | 도착 시각. 구간 이동 시간 계산에 쓴다.                      |
| `departure_time`               | 사용 | 출발 시각. 운행편의 첫 정차 행만 배차 간격 계산에 쓴다.     |
| `stop_id`                      | 사용 | 정류장                                                      |
| `stop_sequence`                | 사용 | 운행편 안의 정차 순서. 정렬 전제 확인에만 쓴다.             |
| `pickup_type`, `drop_off_type` | 무시 | 승하차 가능 여부. 모든 정류장에서 타고 내릴 수 있다고 본다. |
| `timepoint`                    | 무시 | 시각이 실측인지 추정인지                                    |

시각은 `HH:MM:SS`이고 자정을 넘긴 막차를 표현하려고 24시를 넘길 수 있다 (예: `25:10:00`). 그래서 시각 타입이 아닌, 0시부터 흐른 초로 바꿔 계산한다. `04:00:24`는 4×3600 + 0×60 + 24 = 14,424초다.

### 2.4. stops.txt

```csv
stop_id,stop_name,stop_lat,stop_lon
BS_3203_4200001,내곡교,37.746537670,128.887174910
```

| 컬럼                   | 사용 | 설명        |
| ---------------------- | ---- | ----------- |
| `stop_id`              | 사용 | 정류장 ID   |
| `stop_name`            | 사용 | 정류장 이름 |
| `stop_lat`, `stop_lon` | 사용 | 위도, 경도  |

`stop_id`의 앞 두 글자는 정류장 종류를 뜻한다.

| 접두사 | 의미                 |    건수 |
| ------ | -------------------- | ------: |
| `BS`   | 버스 정류장          | 213,625 |
| `RS`   | 철도역 (지하철 포함) |   1,342 |
| `SS`   | 여객선 터미널        |     429 |
| `AS`   | 공항                 |      13 |

버스 ID 중 `BS_TAGO_<nodeId>` 형식은 국토교통부 TAGO 정류장 ID를, 노선의 `BR_TAGO_<routeId>`는 TAGO 노선 ID를 그대로 담고 있다. 지하철역은 `RS_ACC1_S-1-0150`처럼 KTDB 자체 코드를 쓴다.

### 2.5. transfers.txt

```csv
from_stop_id,to_stop_id,transfer_type,min_transfer_time
RS_ACC1_S-1-0150,RS_ACC1_S-1-0426,2,133
```

| 컬럼                         | 사용 | 설명                                                         |
| ---------------------------- | ---- | ------------------------------------------------------------ |
| `from_stop_id`, `to_stop_id` | 사용 | 환승 출발·도착 정류장                                        |
| `transfer_type`              | 사용 | 0 권장 환승, 1 시간 맞춤 환승, 2 최소 시간 필요, 3 환승 불가 |
| `min_transfer_time`          | 사용 | 최소 환승 시간(초)                                           |

KTDB 데이터의 342건은 모두 `transfer_type` 2이고 `min_transfer_time`이 있다. 모두 철도역 간 환승이며, 버스 정류장 간 도보 환승은 이 파일에 없다.

### 2.6. 파일 형식

- 인코딩은 UTF-8이고 줄바꿈은 CRLF다.
- `stop_times.txt`를 제외한 파일은 맨 앞에 UTF-8 BOM(`EF BB BF`)이 있다. BOM이 남으면 첫 헤더 이름이 `﻿route_id`가 되어 컬럼을 찾지 못하므로, 파일을 열 때 첫 글자가 BOM이면 건너뛴다.
- CSV는 Apache Commons CSV로 읽고, 컬럼은 위치가 아닌 헤더 이름으로 찾는다. 컬럼 순서가 바뀐 데이터도 읽을 수 있다.

## 3. 파싱 흐름

운영자가 서버에서 일회성 적재 명령을 실행하면 행정동 경계를 먼저 적재한 뒤 지정한 디렉터리의 GTFS 파일을 아래 순서로 읽는다. 파일마다 처음부터 끝까지 한 번만 읽고, 1.4GB인 `stop_times.txt`도 한 줄씩 흘려 읽어 전체를 메모리에 올리지 않는다.

```bash
sudo /opt/jachwi-sunbae/scripts/import-transit-network.sh \
  --transit.admin-dong.file=/path/to/admin-dongs.geojson \
  --transit.gtfs.directory=/path/to/gtfs
```

| 단계 | 읽는 파일        | 하는 일                                                                              | 결과                 |
| ---- | ---------------- | ------------------------------------------------------------------------------------ | -------------------- |
| 1    | `routes.txt`     | `route_type`이 0·1·3인 노선만 남긴다.                                                | 대상 노선 목록       |
| 2    | `trips.txt`      | 대상 노선의 운행편만 `trip_id → route_id`로 기억한다.                                | 운행편–노선 대응표   |
| 3    | `stop_times.txt` | 대상 운행편의 행만 처리해 정류장, 구간 이동 시간 표본, 첫 정류장 출발 시각을 모은다. | 표본                 |
| 4    | (메모리)         | 구간별 이동 시간 중앙값과 노선별 대기 시간을 계산한다.                               | 구간, 노선 대기 시간 |
| 5    | `stops.txt`      | 3단계에서 실제로 지나간 정류장만 남긴다.                                             | 정류장               |
| 6    | `transfers.txt`  | 양쪽 정류장이 모두 남아 있고 시간을 알 수 있는 환승만 남긴다.                        | 환승                 |
| 7    | (메모리)         | 정류장마다 행정동을 붙이고 수도권 정류장과 그 사이 구간·환승·노선만 남긴다.          | 수도권 노선망        |
| 8    | (DB)             | 기존 `gtfs_*` 테이블을 비우고 새 데이터를 저장한다.                                  | 적재 건수 로그       |

7단계는 적재된 행정동 경계를 쓰므로, 파일을 읽기 전에 행정동이 적재되어 있는지 확인하고 없으면 적재를 실패시킨다 (`POL-COMMUTE-011`). 1~8단계 전체를 한 트랜잭션으로 처리하고, 기존 노선망은 파일을 모두 읽은 뒤인 8단계에서 지운다 (`POL-COMMUTE-006`). 읽기나 저장 중 실패하면 롤백되어 이전 노선망이 그대로 남는다. 전국 데이터는 읽는 데 약 25초가 걸리며, 그동안 DB 커넥션 하나를 점유한다.

### 3.1. 정차 기록에서 구간 만들기

`stop_times.txt`를 위에서부터 읽으며 바로 앞 행과 비교한다.

- 앞 행과 운행편이 다르면 새 운행편의 첫 정차다. 이 행의 `departure_time`을 노선의 출발 시각 표본으로 모은다.
- 앞 행과 운행편이 같고 정류장이 다르면 두 정류장 사이 구간 하나가 생긴다. 이동 시간은 두 행의 `arrival_time` 차이이고, 30초보다 짧으면 30초로 본다 (`POL-COMMUTE-002`).
- 앞 행과 운행편과 정류장이 모두 같으면 같은 정류장이 연달아 기록된 것이므로 구간을 만들지 않는다. KTDB 데이터에 3,461건 있다.

도착 시각끼리 빼므로, 이동 시간에는 앞 정류장의 정차 시간(위 예시에서 10초)이 포함된다.

위 2.3의 네 행으로 만든 구간은 다음과 같다.

| 구간                        |             도착 시각 차이 |     이동 시간 표본 |
| --------------------------- | -------------------------: | -----------------: |
| SEB110000327 → SEB110000286 | 04:00:24 − 04:00:00 = 24초 | 30초 (최소값 적용) |
| SEB110000286 → SEB110000273 | 04:00:59 − 04:00:24 = 35초 |               35초 |
| SEB110000273 → SEB110000272 | 04:01:49 − 04:00:59 = 50초 |               50초 |

첫 행의 출발 시각 `04:00:10`(14,410초)은 노선 `BR_TAGO_SEB100100549`의 출발 시각 표본이 된다.

### 3.2. 정렬 전제

3.1은 같은 운행편의 행이 연속해 있고 `stop_sequence` 순으로 놓여 있어야 맞게 동작한다. GTFS 표준은 행 순서를 보장하지 않으므로, 읽으면서 다음 두 경우를 확인하고 하나라도 걸리면 적재를 실패시킨다 (`POL-COMMUTE-008`).

| 깨진 경우                         | 예시                                     | 그대로 두면 생기는 문제                                       |
| --------------------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| 운행편의 행이 흩어져 있다         | Ord001 행들 사이에 Ord002 행이 끼어 있음 | 한 운행편이 둘로 나뉘어 첫 정차가 두 번 잡히고 구간이 빠진다. |
| `stop_sequence`가 증가하지 않는다 | 1, 3, 2 순서                             | 역방향 구간과 음수 이동 시간이 생긴다.                        |

KTDB 2025-03 데이터는 운행편 326,368개 모두 이 전제를 만족한다.

### 3.3. 구간 이동 시간: 중앙값

같은 노선의 같은 구간(`route_id`, 출발 정류장, 도착 정류장)은 하루 동안 운행편 수만큼 표본이 쌓인다. 대표값은 표본의 중앙값이다. 표본 수가 짝수면 가운데 두 값의 평균을 반올림한다.

노선 100번(`BR_TAGO_SEB100100549`)의 SEB110000327 → SEB110000286 구간은 운행편 112개에서 표본 112개가 나온다.

| 이동 시간 | 30초 | 31초 | 32초 | 33초 | 34초 | 35초 | 36초 | 37초 | 38초 | 40초 |
| --------- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 표본 수   |   63 |    8 |    7 |    7 |   11 |    8 |    4 |    2 |    1 |    1 |

가운데 두 값(56번째, 57번째)이 모두 30초이므로 이 구간의 이동 시간은 30초다. 평균 대신 중앙값을 쓰는 이유는, 시각표 오류로 한두 운행편만 크게 튀는 값이 대표값을 끌어올리지 않게 하기 위해서다.

### 3.4. 노선 대기 시간: 배차 간격의 절반

노선에 탈 때 기다리는 시간은 배차 간격의 절반으로 추정한다. 무작위 시각에 정류장에 도착하면 평균적으로 간격의 절반을 기다리기 때문이다 (`POL-COMMUTE-003`).

1. 노선의 운행편 첫 정류장 출발 시각을 모아 중복을 없애고 정렬한다.
2. 이웃한 출발 시각의 차이(배차 간격)를 구한다.
3. 1분 미만이거나 2시간을 넘는 간격은 이상값으로 보고 뺀다. 같은 시각 중복 기록이나 막차–다음 날 첫차 사이 간격을 걸러내기 위해서다.
4. 남은 간격의 중앙값을 2로 나누고, 2분 이상 15분 이하로 자른다.
5. 남은 간격이 없으면 배차 간격을 10분으로 보고 대기 시간을 5분으로 한다. 운행편이 하나도 없는 노선도 5분이다.

노선 100번은 04:00:10부터 22:30:00까지 출발 시각 112개가 있다. 간격 111개 중 110개가 600초, 1개가 590초이므로 중앙값은 600초이고 대기 시간은 300초(5분)다.

### 3.5. 정류장과 환승 거르기

- 정류장: 3단계에서 대상 운행편이 한 번이라도 정차한 정류장만 남긴다. 일반철도·여객선만 서는 정류장과, 어떤 운행편도 서지 않는 정류장이 빠진다 (`POL-COMMUTE-007`).
- 환승: 출발·도착 정류장 중 한쪽이라도 남지 않았으면 뺀다. `transfer_type`이 3(환승 불가)이거나 `min_transfer_time`이 비어 있는 환승도 걸리는 시간을 알 수 없어 뺀다 (`POL-COMMUTE-004`).
- 같은 정류장 쌍의 환승이 여러 번 나오면 가장 짧은 시간만 남긴다.
- 지역: 행정동 코드가 서울·인천·경기인 정류장만 남긴다. 행정동이 비어 있는 정류장은 남긴 정류장과 구간으로 이어져 있으면 함께 남긴다. 구간과 환승은 양쪽 정류장이 모두 남을 때만, 노선은 남은 구간이 있을 때만 남긴다 (`POL-COMMUTE-024`).

## 6. 판단이 필요한 지점

현재 구현이 단순화한 부분이다. 결과가 이상하면 먼저 확인한다.

- 평일·주말 시간표를 구분하지 않는다. 출퇴근 시간대 정확도가 중요해지면 `calendar.txt`로 평일 운행편만 쓰는 방안을 검토한다.
- 대기 시간은 하루 전체 배차 간격의 중앙값으로 계산해, 출퇴근 시간대의 짧은 간격이 반영되지 않는다.
- 승하차 제한(`pickup_type`, `drop_off_type`)을 무시해, 하차 전용 정류장에서도 탈 수 있다고 본다.
- 버스 정류장 간 도보 환승은 원천 데이터에 없다. 탐색 단계에서 좌표 거리로 도보 환승을 만들지 결정해야 한다.
